## P1 — `<turn_meta>` JSON 메시지 본문 오염 (버그)

### 현상

SC-CTX-RECALL 시나리오 마지막 MEDIATOR 응답(message id=1178):

```
남편분과 함께 풀어보고 싶으신 거네요. 그럼 먼저 당신 마음부터 정리해보면, 남편분한테 꼭 전하고 싶은 게 뭘까요?

```json
<turn_meta>
{
  "horsemen": { ... },
  "user_state": { "state": "NEGOTIATING", ... },
  "issue_delta": { "headline": "남편의 중개자 역할 모색으로 전환", ... }
}
```

charCount: 670 (정상 응답 대비 10배 이상)
```

분석용 메타 블록이 사용자에게 노출되는 채팅 메시지 본문에 그대로 저장되어 있음.

### 원인

`ChatTurnMetaParser`가 LLM 출력에서 `<turn_meta>...</turn_meta>` 블록을 파싱 후 원본 텍스트에서 제거해야 하는데, 제거 로직이 작동하지 않거나 저장 전에 호출되지 않는 경우 존재.

### 수정 위치

- `backend/src/main/java/com/againspring/chat/ChatTurnMetaParser.java`
- `extractAndStrip()` 또는 동등한 메서드가 반환하는 본문 텍스트 확인
- 메시지 저장 호출 전에 반드시 메타 제거 후 본문만 전달하는지 검증

### 기대 수정 결과

메시지 charCount 정상화 (50~100자 수준), 사용자 화면에 JSON 노출 없음.

## P2 — 마크다운 `**텍스트**` 채팅 메시지 노출 (버그)

### 현상

B 환영 메시지 3개 시나리오에서 동일하게 확인:

- SC-FLOW-DUO-CHAT message 1135: `"저는 **다시봄**이라고 불리는 감정 정리 도우미입니다."`
- SC-FLOW-FINALIZE message 1142: `"저는 **다시봄**, 두 분의 감정을 정리하고..."`
- SC-CTX-DUO-TURNS message 1159: `"저는 **다시봄** 감정 정리 도우미입니다."`

마지막 질문도 볼드로 처리됨: `"**지금 마음에 담아두고 계신 것이 있으신가요?**"`

### 원인

LLM이 마크다운 볼드 구문을 출력하고 있으며, BE가 이를 렌더링하지 않고 원문 그대로 저장. FE에서 렌더링된다면 사용자에게는 보이지 않을 수 있으나, 메시지 데이터 자체가 오염됨.

두 가지 선택:

1. BE에서 마크다운 제거 후 저장 (`**` 제거)
2. 프롬프트에서 마크다운 사용 금지 명시

### 수정 위치

- 즉시 적용 가능: `shared/docs/prompts/chat/_response_instructions.md`에 "마크다운 구문(`**`, `_`, `` ` ``) 절대 사용 금지" 추가
- BE 보완: 메시지 저장 전 마크다운 스트리핑 유틸리티 적용 (선택)

## P3 — Duo 모드 A 완전 방치 (품질)

### 현상

SC-FLOW-DUO-CHAT (test1):

| 메시지 ID | 발신자 | 내용 |
|---|---|---|
| 1134 | MEDIATOR_TO_A | 파트너 합류 알림 (자동) |
| 1135 | MEDIATOR_TO_B | B 환영 메시지 |
| 1136 | USER_A | "남편이 제 말을 들으려 하질 않아요. 말하면 방으로 들어가버려요" |
| 1137 | USER_B | "아내가 말을 꺼내면 항상 감정이 먼저 폭발해서..." |
| 1138 | USER_A | "대화가 안 되니까 저도 지쳐서 포기하게 돼요" |
| 1139 | USER_B | "저도 대화하고 싶은데 방법을 모르겠어요" |
| 1140 | MEDIATOR_TO_B | B에게만 응답 |

A는 파트너 합류 알림 이후 2개의 메시지를 보냈으나 MEDIATOR_TO_A 응답 0개.

SC-CTX-DUO-TURNS에서도 동일: A 3개 메시지 → MEDIATOR_TO_A 0개, B 3개 메시지 → MEDIATOR_TO_B 3개.

### 원인 분석

취소 메커니즘이 양쪽 메시지를 동시에 수신하면 마지막 메시지 1개(B)에만 응답하도록 동작. A의 메시지도 취소 큐에 들어가 처리되지 않는 것으로 추정.

또는 Duo 모드에서 `<current_user_message sender="USER_B">` 한 번만 처리하고 USER_A에 대한 응답을 별도로 트리거하지 않는 구조 문제.

### 수정 위치

- `backend/src/main/java/com/againspring/chat/CancelableChatService.java` 또는 동등 서비스
- A와 B가 동시에 메시지를 보낼 때 각각 독립적으로 응답이 생성되는지 확인
- A의 응답과 B의 응답 취소/재실행이 서로 독립적으로 동작해야 함

### 기대 수정 결과

B가 합류해도 A의 다음 메시지에 MEDIATOR_TO_A 응답이 정상 생성됨.

독립적으로도 개선 가능: `duo_chat.md §양쪽 컨텍스트를 활용하는 방법`에서 "상대분도 [본인 메시지 키워드 기반 가설]로 느끼셨을 수 있어요" 형식 활용을 더 적극 권장.
