# v2 창립 진단 — 세 가지 미스매치

> **작성일**: 2026-06-21 · **출처**: 사용자 분석 + v1 결과(D-106~D-108)
> **성격**: v2의 창립 문서. 이 진단이 v2 전체 설계를 결정한다.

---

## 한 줄 진단

세 가지 미스매치가 겹쳐 있었다. **단위(unit)가 틀렸고, 최적화 대상(optimizer)이 틀렸고, 판정자(oracle)가 틀렸다.** 하나만 고쳐도 조금 나아지지만, 셋이 동시에 어긋나 있어서 2주를 갈아도 신호가 안 잡혔다.

---

## 실패 원인 — 레벨별

| 레벨 | v1이 한 것 | 왜 구조적으로 실패했나 |
|---|---|---|
| **Primitive (optimizer)** | Best-of-N 리랭킹 (판별기로 가장 사람 같은 초안 선택) | 판별기 argmax를 고르는 건 "사람다움"이 아니라 판별기의 맹점을 최대로 찌르는 초안을 고르는 것(Goodhart). 게다가 같은 모델·프롬프트가 만든 4개 초안의 분산은 AI↔사람 격차에 비해 미미함 → 후처리 필터로 없는 능력을 만들 수 없음. **D-106이 이걸 확정.** |
| **Metric** | MAUVE A-B (cond4) | 0.97~0.9998로 포화 → 변별력 상실. cond4가 같은 커뮤니티에서 −0.356↔+0.483으로 튄 건 측정이 노이즈였다는 뜻. GPT-2 featurizer는 한국어 단문에 부적합. 그리고 분포 단위 지표인데 탐지는 인스턴스·계정 단위라 **단위가 어긋남.** |
| **Oracle** | LLM proxy (cond5) | proxy 15% vs 오너 84%. stateless judge는 글 하나만 보므로 사람이 실제로 쓰는 채널(주제 반복·게시 패턴·계정의 결)을 구조적으로 못 봄. proxy는 정확히 중요한 차원에서 낙관 편향. **D-101에서 갭이 48~69pp 반대 방향으로 나온 순간 "이 proxy는 못 쓴다"가 결론이었어야 함.** |
| **Process** | R0~R17 고빈도 라운드 | 생성기(Codex/Haiku/Sonnet)·corpus·seed가 동시에 바뀌어 어떤 변화가 무엇 때문인지 귀속 불가. 고정 baseline이 없었음. 매 라운드가 다음 라운드를 "필요"하게 만드는 sunk-cost 모멘텀. |

## 코드베이스 실측 (4-에이전트 감사, 2026-06-21)

진단을 코드 레벨에서 확증함:

**단위 미스매치**
- `ActionExecutor.loadRecentBodies` → `recentOutputsBlock`: 반복 회피용으로만 history 주입. topic trajectory **전무.**
- 모든 POST = i.i.d. 신규 갈등 시나리오. CASUAL은 `RNG.nextDouble() < 0.25` 독립 베르누이(`:346`).
- 자기 과거글 참조·사건 발전·주제 드리프트 = **0**.

**optimizer 미스매치**
- 생성기 파인튜닝 **완전 greenfield** (QLoRA/LoRA/PEFT 코드 없음).
- `Jitter.scheduleReplyWithDelay`(5–60분 리얼 딜레이) **빌드됐으나 미호출** — cadence 균일 burst-per-tick.
- 대댓글 1단계 깊이, 상호작용 cadence 비현실적.

**oracle 미스매치**
- eval 단위 = 단일 POST. 계정 타임라인 eval scaffold는 v1 phase-2에 있으나 **실 작성자 타임라인 아님 + 1인 평가** 약점.

## 현실적으로 개선하려면

핵심은 **메시지가 아니라 계정**을 단위로, **선택이 아니라 생성 능력**으로, **proxy가 아니라 사람**을 기준으로 옮기는 것.

| 레버 | 난이도 | 왜 이게 진짜 레버인가 |
|---|---|---|
| **실제 corpus 파인튜닝 (QLoRA)** | 중-상 | 프롬프트로 손코딩하던 register·길이·주제 분포가 학습으로 자동 매칭됨. 단 이건 토큰 문제가 아니라 데이터 문제 — 311건으론 부족. 커뮤니티당 수천 건 clean real 필요. **데이터 게이트 뒤로 연기.** |
| **계정/페르소나 메모리·일관성** | 상 | 매번 새 갈등글(i.i.d.) 자체가 탐지 신호. 실제 계정은 자기 과거 글을 참조하고, 한 사건이 몇 주에 걸쳐 발전하다 드리프트함. 주제 다양화가 아니라 **주제 궤적**이 필요. |
| **게시 cadence·상호작용** | 중 | 10분 틱·top-post만/대댓글 없음 = 글 품질과 무관한 계정 단위 거대 신호. 리랭킹에서 대댓글을 빼버린 게 정확히 계정 humanness가 사는 곳을 뺀 것. |
| **eval을 타깃에 정렬** | 중 | proxy·포화 MAUVE 폐기. 유일한 유효 신호 = 계정 타임라인 단위 사람 블라인드. 저빈도 고정보 eval, 각 회차를 named-tell 라벨셋으로 취급해 결정론적 제거. |
| **판별기는 QA로만** | 하 | Best-of-N 말고, 판별기 feature attribution으로 tell 진단 → 생성/후처리에서 제거. |

## 그런데 이게 가능한가 (냉정하게)

- **캐주얼 독자 대상**: 사실상 이미 됨. CASUAL 글은 오너도 70% 못 잡았음.
- **봇을 작정하고 찾는 참여 멤버 대상, 몇 주 관찰**: 거의 불가능에 가깝고, 그 이유가 생성 품질이 아님. cadence·상호작용·주제 궤적·출처(provenance) 같은 계정 단위 신호 + 움직이는 적대 표적.
- **그래서 "더 개선"의 진짜 질문**: "더 튜닝"이 아니라 "**어느 bar가 실제로 필요한가**". **v2 bar = 계정·캐주얼.**

## 전이되는 교훈 (WaggleBot/ASM 페르소나용)

1. **타깃 단위를 먼저 정하라.** 메시지 품질을 최적화하는데 평가가 계정/채널 단위면 영원히 어긋남.
2. **proxy를 진짜 기준에 검증한 뒤에만 써라.** 한 번 검증해서 갭이 크면 그 proxy는 폐기. proxy 사다리 금지.
3. **변수를 고정하라.** 생성기·데이터·seed 중 하나만 바꿔 고정 eval에 측정.
4. **저빈도 고정보 eval.** 사람 평가는 비싼 ground truth이자 named tell 라벨셋. tell을 결정론적으로 잡는 게 리랭킹보다 싸고 확실.
5. **kill criterion을 미리 박아라.** 종료 결정을 내리는 것이 프로젝트 전체에서 가장 잘한 판단일 수 있음.
