# 다시봄 UX 원칙 (UX Principles)

> **이 문서의 위치**: 본 문서는 다시봄(Again Spring) 프론트엔드의 **사용자 경험 결정 기준**을 정의합니다. 디자인 시스템(`ui/design-handoff.md`)이 *어떻게 보이는가*를 다룬다면, 이 문서는 *왜 그렇게 작동해야 하는가*를 다룹니다. 새로운 화면을 만들거나 기존 화면을 수정할 때, 그리고 PR 리뷰 시 이 문서를 체크리스트로 활용합니다.
>
> **권위 관계**: 본 문서는 FE UX 권위본입니다. 단, 카피·금지어·위기 감지·기여도 산식 같은 *서비스 정책*은 `../../../shared/docs/policies/`가 권위본이며, 본 문서는 그 정책을 *어떻게 UX로 구현할지*만 정의합니다.
>
> **현재 기준**: V1.5 카톡식 채팅 + Phase A/B/C 중재 컨텍스트 강화 (2026-04-27).
>
> **자매 문서**: [`./hax-checklist.md`](./hax-checklist.md) — 본 문서의 *원칙 1군*을 컴포넌트별 PR 체크리스트로 풀어낸 것.

## 0. 다시봄이 일반 SaaS와 다른 이유

다시봄의 사용자는 **갈등 한복판에 있는 두 사람**입니다. 이 도메인적 사실이 모든 UX 결정의 출발점입니다.

1. **사용자는 일시적으로 인지 부하 상태입니다.** 분노·슬픔·불안·자기 방어가 평소의 판단력을 떨어뜨립니다. 일반 사용자라면 무리 없이 따라갈 플로우가, 갈등 상태에서는 두 배로 무겁게 느껴집니다.
2. **시스템이 한쪽 편을 든다고 느끼는 순간 신뢰가 무너집니다.** AI 중재자의 미세한 단어 선택, 호명 순서, 색상 비중 하나가 "나만 잘못한 것 같다"라는 느낌을 줄 수 있습니다.
3. **잘못 설계된 기능은 무기가 됩니다.** 초대 링크, 상대방 메시지 메타데이터, 결과 리포트 — 모두 가해 도구로 변질될 가능성이 있습니다. "선의의 디자인"으로는 부족하며, "악용 시나리오를 명시적으로 차단하는 디자인"이 필요합니다.
4. **사용자가 위기 상태일 수 있습니다.** 가정폭력·자해·아동학대가 갈등의 배경에 있을 수 있고, 다시봄은 그 신호를 가장 먼저 받는 인터페이스가 됩니다.

따라서 다시봄의 UX는 다음 4개 원칙군을 따릅니다.

- **원칙 1군 — AI 중재자 신뢰성** (Microsoft HAX 18 Guidelines)
- **원칙 2군 — 위기 사용자 보호** (Process for Inclusive Safety, SAMHSA 6원칙)
- **원칙 3군 — 인지 부하 최소화** (GOV.UK Service Manual, NN/g 원칙)
- **원칙 4군 — 결과 해석의 안전성** (WCAG 2.2 cognitive, Do No Harm Guide)

각 원칙군은 우선순위가 있습니다. 1, 2군은 **즉시 적용**, 3군은 **플로우 정비 시 적용**, 4군은 **점진적 보완** 영역입니다.

## 0.1 V1.5 현행 플로우 (참고)

이 문서가 가정하는 사용자 흐름:

```
/ (랜딩)
  → /onboarding/intro → /onboarding (10문항) → /onboarding/result → [선택: mbti-test/input]
  → /auth/signup or /auth/guest (선택)
  → /session/new (관계 유형)
  → /session/category (대분류 + 소분류, 직접 입력 가능)
  → POST /api/sessions → 즉시 세션 생성
  → /session/chat/[id] (카톡식 자유 채팅, ChatLayout)
       ┌─ Solo: ChatPanel 단독
       └─ Duo: SwipeContainer(ChatPanel | PartnerPanel)
       사용자 메시지 ≥3 시 finalize 가능
       MediatorMessage = chat 안의 MEDIATOR_TO_A/B 메시지
  → /session/result/[id] (Duo 완료) 또는 /session/result/[id]/solo (Solo)
  → /history → /session/history/[id] (과거 이력 보기)
```

핵심 변화: **6턴 mediation → 자유 채팅**, **describe/invite/wait 단계 폐기**, **AI 메시지 = 채팅 메시지의 한 종류**.

## 원칙 1군 — AI 중재자 신뢰성

기준: Microsoft HAX Toolkit, *Guidelines for Human-AI Interaction* (Amershi et al., CHI 2019). 18개 가이드라인 중 다시봄에 직접 영향을 주는 항목만 발췌·번역해 다시봄 컨텍스트로 재해석합니다. 컴포넌트 단위 점검 항목은 [`./hax-checklist.md`](./hax-checklist.md).

### 1.1 AI가 무엇을 할 수 있고 없는지 처음에 명시한다 (HAX G1, G2)

다시봄의 AI 중재자는 *판결자*가 아니라 *번역기*입니다. 양쪽의 말을 상대 입장에서 다시 들리도록 정리할 뿐, 누가 옳은지 결정하지 않습니다. 이 사실을 사용자가 처음 만나는 화면에서 명시적으로 알려야 합니다.

**적용 화면**: `/`, `/onboarding/intro`, `/session/category` (세션 생성 전 마지막 단계), `/session/chat/[id]` (첫 진입)

**구현 규칙**:
- 첫 세션 진입 직전 (현재는 `/session/category`에서 카테고리 선택 → 세션 생성 → `/session/chat/[id]` 이동), 다음 4가지를 **첫 진입 시 1회 카드 또는 빈 채팅 placeholder**로 보여줍니다:
  - "AI는 누가 옳은지 판단하지 않습니다"
  - "AI는 양쪽이 어떤 마음으로 그렇게 행동했는지 정리해 보여줍니다"
  - "AI도 틀릴 수 있습니다. 답변이 어색하면 자유롭게 다시 말씀해 주세요"
  - "감정적으로 힘든 순간에는 언제든 멈출 수 있습니다"
- `ChatPanel`의 `EmptyChatPlaceholder` ("무슨 일이 있으셨어요? / 편한 말로, 카톡처럼 한 줄씩 적어주세요. / 제가 차분히 들을게요")는 G1·G5의 부분 적용입니다 — **여기에 G1·G2 한계 진술 한 줄을 추가**하는 것이 가장 자연스러운 위치입니다.
- AI 메시지(`MEDIATOR_TO_A` / `MEDIATOR_TO_B` sender)는 사용자 메시지와 시각적으로 명확히 구분되어야 합니다 — 현재 `MessageBubble`은 `isMine` 기준으로 좌·우만 구분합니다. **AI 메시지에 작은 라벨이나 아바타**가 필요한지 검토 가치가 있습니다.

### 1.2 AI 답변이 마음에 안 들 때 빠져나갈 수 있어야 한다 (HAX G9)

V1.5 카톡식 구조에서는 6턴 mediation처럼 *명시적 재생성 버튼*을 두기 어렵습니다. 대신 **자유 채팅 자체가 G9의 자연스러운 적용**이 됩니다 — 사용자는 다음 메시지로 *언제든 보충/정정*할 수 있습니다.

**구현 규칙**:
- AI 정리가 어색할 때 사용자가 "그게 제 마음과는 좀 달랐어요. 다시 말하면…" 같은 *후속 메시지*를 보내는 것이 자연스럽도록, AI 응답 직후 입력창은 **항상 비활성화 없이** 살아있어야 합니다.
- `EmptyChatPlaceholder` 또는 첫 AI 응답 직전 안내에 "정리가 어색하게 느껴지면 이어서 말씀해 주세요. 같은 마음을 다른 말로 다시 적어주셔도 좋아요" 같은 *재정정 권장 카피*를 1회 노출합니다.
- `FinalizeSuggestionCard`의 "더 이야기할래요" 버튼은 G9의 명시적 적용입니다 — 이 패턴을 유지·강화합니다.

### 1.3 결과의 근거를 묻는다면 보여줄 수 있어야 한다 (HAX G11)

화해 기여도 `55:45`, 욕구 차이 지도 같은 수치는 그 자체로 강력한 인지적 무게를 가집니다. 사용자가 "왜 이 숫자인가요?"를 물을 수 있어야 하며, 그 질문에 답할 수 있어야 합니다.

**현재 구현 상태 (양호)**:
- `ContributionRatio` 컴포넌트의 *법적 안내문구 박스* — "이 수치는 두 분의 회복 시작점을 부드럽게 안내하기 위한 참고용이에요. 법적 판단이나 과실 비율과는 무관하며, AI 분석에는 한계가 있어요. 깊은 갈등은 전문 상담을 권해드려요." — 이미 G11 + G2의 모범적 적용입니다. 유지합니다.
- `conflictType` 기반 보조 카피 ("두 분 모두 잘못한 게 아니라 다를 뿐이에요" / "이번 상황에서는 한쪽의 책임이 좀 더 분명해 보여요") — G11의 *맥락 설명*입니다.

**보강 권장**:
- `NeedsMap`의 두 점 위치 산출 근거가 현재 사용자에게 노출되지 않습니다. 점 옆 또는 카드 하단에 `?` 아이콘을 두고 탭 시 "이번 대화에서 ㅇㅇ님은 *연결*보다 *공간*을 더 자주 언급하셨어요" 같은 *맥락적 한 줄*을 보여줍니다. 알고리즘 자체 노출은 불필요.

### 1.4 사용자에게 통제권을 돌려준다 (HAX G8, G17)

사용자는 언제든 멈출 수 있어야 합니다. 모달 안에 갇힌 느낌은 갈등 사용자에게 *지배당하는 느낌*을 재현시킵니다.

**구현 규칙**:
- 채팅 화면 우상단 `ChatHeader`에 "잠시 멈추기" 또는 "나가기" 동작이 항상 1탭 안에 있어야 합니다. (현재 `ChatHeader`에 `onFinalize`, `onOpenInvite`만 있음 — *명시적 종료/일시 중단 버튼* 추가 검토 필요.)
- 누른 시점까지의 입력은 자동 저장 (현재 BE가 메시지를 영속화하므로 자연스럽게 보존됨).
- 같은 사용자가 24h 내 같은 세션 URL로 돌아오면 그대로 이어집니다. 이력 화면(`/(dashboard)/history`)의 `ACTIVE_STATUSES` 필터가 진행 중 세션을 노출하므로, 해당 세션을 탭하면 곧장 채팅으로 돌아갑니다 — 유지합니다.
- 세션 단위 삭제 옵션은 `/(dashboard)/history`에 이미 멀티셀렉트 + 삭제 확인 모달로 구현됨 — 유지합니다.

### 1.5 AI 답변이 어색할 때를 우아하게 다룬다 (HAX G10)

AI가 입력의 의도를 잘못 파악할 때 — 한국어 비표준 표현, 줄임말, 사투리, 욕설 섞인 감정 표현 — 무리해서 답하기보다 **확인 또는 일반적 응답**을 합니다.

**구현 규칙**:
- BE의 LLM 응답이 *낮은 confidence* 신호를 줄 경우 (현재 시스템에 신호가 있다면), AI 메시지에 "혹시 이런 마음을 말씀하신 건가요?" 같은 disambiguation을 우선합니다. 현재 시스템이 그런 신호를 주지 않는다면, 이 항목은 BE/LLM 프롬프트 측 보강 요청입니다.
- 절대 추측한 답을 *단정적*으로 내놓지 않습니다. 카피 톤은 항상 가정형 ("~하셨을 수 있어요", "~처럼 느끼셨을 것 같아요") — 이미 디자인 시스템에 명시됨.

### 1.6 사회적 편향을 피한다 (HAX G6)

다시봄은 두 사람 사이에서 작동하므로, AI의 한 단어가 한쪽에 유리하게 들리는 순간이 가장 큰 위험입니다.

**구현 규칙**:
- BE의 `MediatorMessage` 생성 시 *호명 순서 균형* — A 다음 턴엔 B를 먼저 언급. (FE 측이 아닌 BE/프롬프트 책임이지만, FE는 결과를 검증할 수 있어야 함.)
- `ReportLayout`의 색상 면적 균형: A 피치(`var(--P-a)`), B 세이지(`var(--P-b)`)가 동등하게 사용됨. **`ContributionRatio` 바 차트는 비율 그대로 보여주지만 (예: 55:45 → A 면적이 더 큼)**, 이건 의도된 정보 전달이므로 허용. 단 *위계*는 동등하게 표시됨.
- 사용자 시점에 따라 자기 자신이 먼저·왼쪽에 표시되도록: 현재 `ReportLayout`은 `myRole`을 받아 `myName`/`partnerName`을 추출하지만, **NeedsMap의 두 점 위치는 항상 A·B 절대 좌표**입니다. 시점별 좌표 회전을 검토할 가치가 있습니다 — 단, 두 사용자가 같은 리포트를 보고 비교할 가능성을 고려해야 함.
- 카피·요약에서 두 사람을 묘사하는 형용사·부사의 강도가 균형 잡혔는지 검사하는 lint 규칙 추가 검토 (`shared/docs/policies/forbidden-words.md` 권위본을 따라 구현).

### 1.7 한 번 멈춤은 한 번 멈춤이지, 처벌이 아니다 (HAX G3)

AI 중재자는 사용자의 페이스를 존중해야 합니다. 채팅 입력 중 머뭇거림, 긴 침묵, 백스페이스가 잦은 패턴은 사용자가 *생각하고 있다*는 신호입니다.

**구현 규칙**:
- `ChatInput`은 카운트다운, 시간 제한, "왜 답이 없으세요?" 알림 어느 것도 표시하지 **않습니다** (현재 양호).
- "전송" 버튼은 입력 가능해진 즉시 활성화되지만, 카운트다운 표시는 금지합니다 (현재 양호).
- AI 응답 중 `TypingBubble`은 적절한 G3 시그널입니다 ("중재자가 응답을 작성 중입니다" `aria-label`) — 유지합니다.

### 1.8 다시봄에서 *적용하지 않는* HAX 가이드라인

투명성을 위해, 18개 중 다시봄이 의도적으로 *적용하지 않는* 항목을 명시합니다. 이 항목들은 다시봄의 데이터 보존 정책(30일 만료) 및 양방향 비대칭 구조와 충돌합니다.

- **G12 Remember recent interactions**: 다시봄은 30일 후 자동 만료, AI가 먼저 과거를 꺼내지 않습니다. 사용자가 `/history`에서 *수동으로* 과거 세션을 열 수 있을 뿐, 새 세션의 AI 응답이 "지난번 ㅇㅇ과의 대화에서…"를 자동 인용하지 않습니다.
- **G13 Learn from user behavior**: 개인화 학습은 도입하지 않습니다. AI가 한쪽의 패턴을 학습해 다른 쪽에게 더 호의적이 될 위험이 큽니다. 단, *세션 내 컨텍스트* (Phase A/B/C — UserProfileFragment, PsychologyFeedbackFormatter, DuoBalanceFormatter)는 적용 — 이는 학습이 아닌 *현재 세션 추론*이므로 G12·G13 비적용 정신과 양립합니다.
- **G15 Encourage granular feedback**: 채팅 *중* 만족도/평가를 묻지 않습니다. 갈등 한복판의 평가는 신뢰할 수 없고, 평가 행위 자체가 사용자의 부담을 늘립니다. 결과 화면 이후에만 가볍게 묻는 것을 검토합니다.

## 원칙 2군 — 위기 사용자 보호

기준: Eva PenzeyMoog, *Design for Safety* (A Book Apart, 2021)의 *Process for Inclusive Safety* 5단계, SAMHSA의 *Trauma-Informed Approach* 6원칙. 다시봄은 PenzeyMoog가 챕터 7에서 별도로 다루는 **"취약 집단을 위한 제품"** 영역에 가깝습니다 — 일반 제품에 안전을 추가하는 게 아니라, 처음부터 취약 사용자를 1순위에 두고 설계해야 합니다.

### 2.1 모든 신규 기능은 *악용 시나리오*를 먼저 그린다

PenzeyMoog의 5단계 (Research → Archetypes → Brainstorm → Solutions → Test) 중 처음 3단계를 다시봄에 맞게 압축한 *피처 시작 체크리스트*입니다.

**구현 규칙 (PR 템플릿에 포함)**:
새 화면, 새 입력 필드, 새 외부 공유 기능, 새 알림 채널을 추가하는 PR은 반드시 다음 4개 질문에 답해야 합니다.

1. **Abuser archetype**: 가해자가 이 기능을 어떻게 무기로 쓸 수 있는가? (예: 초대 링크 강요, 상대방 메시지 메타데이터를 추궁 도구로 사용, 결과 공유 카드를 비난 도구로 사용)
2. **Survivor archetype**: 학대 상황에 있는 사용자가 이 기능을 사용할 때 새로 노출되는 위험은? (예: 알림 미리보기에 갈등 내용이 노출되어 같은 집에 사는 가해자에게 보임, 카톡 공유 시 메타데이터 노출)
3. **Roadblock**: 이 악용을 *기능적으로* 막을 수 있는가? 못 막는다면 *마찰*은 어디에 둘 것인가?
4. **Exit path**: 이 화면에서 사용자가 위협을 느꼈을 때 1탭으로 빠져나갈 수 있는가? 빠져나간 흔적이 최소화되는가?

### 2.2 양쪽 데이터는 격리된다 (Trustworthiness & Transparency)

A의 입력을 B가 볼 수 있는 시점, B의 입력을 A가 볼 수 있는 시점이 명확해야 합니다. 그리고 그 시점은 *시스템이 결정*하지 *상대방이 결정*하지 않습니다.

**현재 구현 상태 (모범 사례)**:
- `PartnerPanel`은 V1.5의 핵심 안전 디자인입니다. Duo 모드에서 사용자는 상대 메시지 *메타데이터만* 볼 수 있습니다 — `BlurredBubble`이 글자 수와 시간만 표시하고 본문은 블러 라인으로 가립니다. "내용은 두 분의 사생활 보호를 위해 가려져 있어요"라는 *명시적 카피*까지 있습니다. 이 패턴은 유지·강화합니다.
- `InviteModal` 카피 "상대분이 합류해도 두 분의 대화는 서로 보이지 않아요. 제가 양쪽 마음을 따로 듣고, 균형있게 정리해드려요" — 데이터 격리를 사용자가 *초대 시점*에 알 수 있게 합니다. 유지합니다.
- 양쪽 결과는 결과 리포트에서만 공유되며, **원문은 공유되지 않습니다** — `MEDIATOR_TO_A`와 `MEDIATOR_TO_B` sender 분리로 BE 레벨에서 격리됨.

**보강 권장**:
- `ChatInput`에 입력 중 "이 글은 AI가 정리해서 ㅇㅇ님께만 전달돼요. 원문 그대로는 전달되지 않아요" 같은 *항상 보이는 작은 안내*를 검토합니다 (현재 placeholder만 있음).
- `ShareCardRatio`, `ShareCardBlurredLetter`, `ShareCardMetaphor` — 외부 공유 카드에는 **갈등 원문이 절대 미포함**되어야 합니다. PR 시 이를 자동 검증할 수 있는 lint 또는 unit test 추가 가치 있음.

### 2.3 위기 신호는 다른 모든 것을 우선한다 (Safety)

V1.5 현재 두 개의 위기 모달이 공존합니다:
- `components/chat/CrisisModal.tsx` — 채팅 sending이 거부될 때 표시
- `components/shared/CrisisResourceModal.tsx` — 다른 진입점용

**현재 구현의 갭**:
- 두 모달 모두 **바깥 클릭과 ESC로 닫힙니다**. `chat/CrisisModal`은 `onClick={onClose}`로 명시적으로 바깥 클릭 닫기를 허용하고, `shared/CrisisResourceModal`은 `handleEscape` 핸들러가 `onClose()`를 호출합니다.
- 이는 PenzeyMoog *Design for Safety*의 "사용자가 위기 상황에서 실수로 안전망을 떨쳐내지 못하게" 원칙과 충돌합니다.
- `frontend/docs/policies/crisis-modal.md`의 *명시적 권장*("ESC 무시 — 사용자가 의도적으로만 닫을 수 있음")과도 코드가 일치하지 않습니다.

**원칙으로 못 박아둘 사항**:
- **위기 모달은 dismiss 마찰을 *의도적으로* 두어야 합니다.** ESC 키, 바깥 영역 클릭, 뒤로가기 어느 것으로도 닫히지 않으며 명시적 액션 버튼("알겠어요" 또는 "닫기")으로만 닫힙니다.
- **두 모달의 거동은 동일해야 합니다.** 같은 위기 상황에서 어느 진입점이냐에 따라 닫힘 방식이 다른 것은 사용자에게 일관성 손상입니다.
- **위기 키워드 감지 시 세션 데이터는 즉시 일시 정지됩니다.** BE는 이미 `crisisLevel === 1` 응답으로 *서버가 메시지를 거절*하므로 자동 정지됨 — 유지.
- **핫라인 정보는 캐시된 정적 자원에서 제공됩니다.** 네트워크 실패 시에도 1366, 1393, 132, 112, 119, 1388이 항상 보여야 합니다 — `lib/constants/crisisResources.ts` 정적 import로 만족됨.
- **위기 핸들링은 BE와 FE 양쪽에 이중 구현됩니다.** 클라이언트 우회를 가정합니다. 현재 `ChatInput`이 클라이언트 사이드 검사를 하고 BE의 `KeywordGuard`가 서버 사이드 검사 — 이중화 유지.

### 2.4 사용자에게 선택권과 목소리를 돌려준다 (Empowerment, Voice & Choice)

갈등 사용자는 종종 자기 결정권을 잃은 상태에서 다시봄에 도착합니다. 디자인은 그 결정권을 *되돌려 주는* 도구여야 합니다.

**현재 구현 상태 (양호)**:
- `InviteModal`의 3개 톤 ("부드럽게/가볍게/진지하게") 선택 — 사용자가 *어떻게* 초대 메시지를 보낼지 선택권을 가집니다. 유지.
- `InviteModal`에서 **자동 발송이 없습니다** — `navigator.share` 또는 클립보드 복사로 *사용자가 직접* 보냅니다. 유지.
- `FinalizeSuggestionCard`의 "정리하기" / "더 이야기할래요" — 양 옵션이 동등 위계 + 동등 시각 비중. 유지.
- 카테고리 선택 단계에서 "직접 입력" 옵션 (`allowCustomInput`) — 사용자가 분류에 갇히지 않게 함. 유지.

**보강 권장**:
- 결과 리포트의 외부 공유 (`ShareCardRatio` 등) — **명시적 동의** 없이 절대 자동 발생하지 않습니다. 현재 사용자가 명시적으로 공유 버튼을 눌러야 하므로 양호. 이 정신을 유지합니다.
- 채팅 화면에 "이 세션 그만두기 / 삭제하기" 옵션이 헤더 메뉴에 있어야 합니다. 현재 `ChatHeader`에는 invite/finalize만 있어 보강 검토 필요.

### 2.5 비대칭은 인정하되 굴욕은 만들지 않는다 (Collaboration & Mutuality)

다시봄에서 A는 시작자, B는 초대받은 자입니다. 이 비대칭은 구조적이지만, B를 *수동적·약자*로 묘사하면 안 됩니다.

**현재 구현 상태 (양호)**:
- `InviteModal`의 카피 — "함께 정리하면" / "같이 해볼래?" — 강요·의무화 톤이 아닙니다. 유지.
- Solo→Duo 전이 시 `PartnerJoinedToast` — 환영 톤. 유지.
- B가 24시간 내 미참여여도 Solo 모드는 *별도 라우트가 아닌 동일 세션*입니다 (status `chatting_solo` 유지). B가 나중에 와도 자연스럽게 합류 가능. 비차선책 디자인 — 유지.

**원칙으로 유지할 사항**:
- B 진입 화면(`/session/join/[token]`)의 카피는 "당신을 초대한 분이 다음과 같이 말했습니다" 같은 *상대 의무화 카피* 사용 금지.
- A의 대기 표현은 "B의 응답을 기다리는 중" ✗ → "두 분이 같은 시간에 만나기 어려울 수 있어요" ✓ — V1.5에선 별도 wait 화면이 없고 chat 안에서 메시지만 쌓이므로 자연스러움.
- Solo 모드 결과(`SoloResult`, `ContributionRatio` Solo 분기)는 *차선책* 표현이 아닌 *현재 시점 결과*로 제시 — 현재 ContributionRatio Solo 분기 카피("화해 기여도는 상대방이 함께 참여했을 때 안내드릴 수 있어요. 지금은 ㅇㅇ님 한 분의 관점으로 분석한 결과예요")가 양호. 유지.

### 2.6 문화·언어·맥락에 대한 겸손 (Cultural, Historical, Gender Issues)

다시봄은 한국어 사용자를 1차 타깃으로 합니다. 이 사실이 카피·기본값·예시에 일관되게 반영되어야 하며, 동시에 다양한 관계 형태를 가정합니다.

**현재 구현 상태 (양호)**:
- `/session/new` 관계 옵션: "연인·썸 / 부부 / 친구 / 가족 / 부모·자식" — 친밀 관계만 정상화하지 않고 친구·부모·자식 동등 위계. 유지.
- 디자인 시스템이 이미 "하트, 마스코트" 같은 친밀 관계 전제 시각 요소를 금지함 — 유지.
- 성별·연령을 묻지 않음 — 유지.

**원칙으로 유지할 사항**:
- 카테고리에 "데이트 폭력", "가스라이팅" 같은 항목을 포함시킬 때는, 해당 항목 선택 시 즉시 위기 모달이 아닌 *연결 자원 카드*로 부드럽게 안내합니다 — 사용자가 자기 상황을 그렇게 정의하지 않을 수도 있습니다.
- 결과 리포트의 `powerImbalanceDetected === true` 시 ContributionRatio를 *숨기고* 위기 자원 박스를 노출 — V1.5에 이미 구현됨, 유지.

### 2.7 Stress testing은 필수 단계입니다

*Design for Real Life* (Meyer & Wachter-Boettcher)에서 가져온 개념입니다. 다시봄의 모든 핵심 화면은 다음 4개 stress 시나리오로 테스트해야 합니다 (PR 머지 전).

1. **분노 직후 시나리오**: 사용자가 30분 전에 크게 다툰 직후 들어왔다. 손이 떨리고 오타가 많다.
2. **우울/소진 시나리오**: 사용자가 며칠째 잠을 못 잤다. 긴 글을 읽기 어렵다.
3. **공포 시나리오**: 사용자는 같은 공간에 가해자가 있는 상태에서 다시봄을 연다. 알림 소리, 화면 미리보기가 위험하다.
4. **이별 직후 시나리오**: 관계가 이미 끝났을 수도 있다. 화해를 전제하는 카피가 모욕적으로 느껴진다.

각 시나리오에서 화면이 사용자를 *더 다치게* 하지 않는지를 확인합니다.

## 원칙 3군 — 인지 부하 최소화

기준: GOV.UK Service Manual의 *one thing per page*, *question pages*, *task list* 패턴, NN/g의 인지 부하 감소 원칙. 갈등 상태의 사용자는 일시적 인지 부하 상태에 있습니다. 정부 서비스가 "스트레스 받은 시민이 제대로 작동하게 돕는" 노하우를 축적해 온 것과 같은 원칙이 필요합니다.

### 3.1 한 화면에 한 가지만 묻는다 (One thing per page)

**현재 구현 상태**:
- `/session/new` (관계 1개), `/session/category` (카테고리 2단계) — 한 화면 한 결정. 양호.
- 온보딩 10문항도 `LikertQuestion`으로 한 화면 한 질문 + auto-advance. 양호.
- `ChatInput`은 단일 textarea — 양호.

**원칙으로 유지할 사항**:
- 새 화면 추가 시 한 화면 한 질문 원칙을 유지합니다.
- 단, 정확히 같이 묶여야 의미가 있는 정보는 한 화면에 둘 수 있습니다 (GOV.UK 예외 인정).

### 3.2 진행 상태는 항상 보이되, 시계가 되지는 않는다

**현재 구현 상태**:
- `Dashes` 컴포넌트로 4단계 표시 (`<Dashes n={4} done={1} />`) — 디자인 시스템의 `■ ■ — —` 패턴과 일치. 양호.
- 채팅에는 진행률 표시 없음 — 카톡식이므로 자연스럽고, 강제 끝점이 없으므로 양호.

**보강 권장**:
- `canFinalize` 조건(사용자 메시지 ≥3) 충족 시 `ChatHeader`에 *부드러운* 신호 ("이제 정리해도 될 것 같아요" 같은 *제안* 톤) — 현재 `canFinalize`가 헤더 버튼 활성화 토글로만 쓰임.

### 3.3 카톡식 채팅에 적용되는 wizard 원칙

V1.5는 wizard 단계를 줄였지만, *결정의 순간*은 여전히 wizard 원칙을 따릅니다.

**적용 지점**:
- `FinalizeSuggestionCard` — "정리하기 / 더 이야기할래요" 결정. 이 카드 안에서 사용자는 한 번에 한 결정만 합니다. 양호.
- `InviteModal` — 톤 선택, 메시지 편집, 공유 — 한 화면 안에서 자연스러운 순서. 양호.

### 3.4 의미 있는 버튼 라벨을 쓴다

NN/g 권장. "다음", "확인" 같은 일반 라벨은 정보 가치가 없습니다.

**현재 구현 상태 (대체로 양호)**:
- "초대 링크 만들기" / "카톡으로 공유하기" / "정리하기" / "더 이야기할래요" — 행동 명시. 양호.
- 일부 "다음" 버튼은 카테고리 선택 같은 단순 진행에는 허용 가능.

**원칙**: 감정 부하가 큰 결정 직전에는 일반 라벨 ("확인" / "다음") 대신 *결과 행동*을 라벨에 담습니다.

### 3.5 뒤로 가기는 항상 작동한다

**현재 구현 상태**:
- 모든 화면에서 브라우저 뒤로 가기는 데이터를 잃지 않고 작동 (Zustand persist).
- 화면 안의 `PhoneHeader`의 `onBack` 핸들러도 동일하게 동작.
- 결제 같은 되돌릴 수 없는 액션 부재 — 안전.

### 3.6 중간 저장과 재개

**현재 구현 상태 (양호)**:
- BE가 모든 메시지를 영속화 — 자연스럽게 보존.
- `/(dashboard)/history`에서 진행 중 세션(`ACTIVE_STATUSES`)을 진입 가능.
- 온보딩 답변도 `useUserStore.onboardingAnswers`로 보존.

## 원칙 4군 — 결과 해석의 안전성

기준: WCAG 2.2의 신규 cognitive 항목, Urban Institute의 *Do No Harm Guide*. 결과 리포트는 다시봄에서 가장 큰 영향력을 가진 화면입니다 — 한 줄의 잘못된 표현이 관계를 더 망가뜨릴 수 있습니다.

### 4.1 사람을 먼저, 라벨을 나중에 (Do No Harm Guide)

수치와 분류는 사람을 *묘사*하는 것이지 *정의*하는 것이 아닙니다.

**현재 구현 상태 (양호)**:
- `ContributionRatio` 카피 "이번 상황에서는 한쪽의 책임이 좀 더 분명해 보여요" — *시간 한정사* "이번 상황에서는" 사용. 양호.
- `ReportLayout`의 `conflictType` 카피 "누구의 잘못이라기보다, 두 분이 서로 다른 방식으로 필요로 하는 것들이 있었어요" — 처벌 회피. 양호.
- `StyleCombination` (6×6 조합) 컴포넌트가 결과 카피에 *영구적 진단*을 쓰지 않는지 확인 가치 있음.

**원칙으로 유지할 사항**:
- "당신은 회피형입니다" ✗ → "이번 대화에서는 회피하는 모습이 보였어요" ✓
- 모든 결과 카피는 "이번 대화에서", "이 순간에"라는 시간 한정사를 포함합니다.

### 4.2 라벨 순서는 의도적으로

A를 항상 왼쪽·먼저 두면 B가 부수적으로 보입니다.

**현재 구현 상태**:
- `ReportLayout`은 `myRole`을 받아 `myName`/`partnerName`으로 풀어서 사용 — *시점별 카피*는 적용되지만 *시각화 좌표*는 절대값. 부분 적용.
- A 피치, B 세이지 — 색상 면적은 동등.
- `ContributionRatio` 바 차트는 의도적으로 비율 면적으로 표현 (정보 전달).

**보강 권장 (장기)**:
- `NeedsMap`에서 사용자 시점에 따라 자기 점이 *가까운 쪽*에 표시되도록 하는 옵션 검토. 단, 두 사용자가 같은 리포트를 비교할 가능성 (예: 카톡 캡처 공유) 때문에 *일관성 손상 위험*이 있어 신중 검토 필요.

### 4.3 수치는 *반올림된 관찰*임을 디자인으로 보여준다

**현재 구현 상태 (모범)**:
- `ContributionRatio` 하단 박스: "이 수치는 두 분의 회복 시작점을 부드럽게 안내하기 위한 참고용이에요. 법적 판단이나 과실 비율과는 무관하며, AI 분석에는 한계가 있어요." — 정밀 측정값 오해 방지의 정확한 적용. 유지·강화.

**원칙**:
- 절대 비교 금지: "지난번보다 0.3°C 올랐어요" 같은 문구는 데이터 정밀성을 과장합니다.
- 수치를 *결정의 근거*로 쓰지 않습니다. "55:45이니 A가 더 노력해야 합니다" 같은 처방을 절대 내리지 않습니다 — 현재 카피는 양호.

### 4.4 위기 정보는 결과 리포트 안에 *항상* 있다

**현재 구현 상태 (모범)**:
- `ReportLayout`의 `powerImbalanceDetected === true` 분기 — 위기 자원 박스 자동 표시 (1366, 1577-0199, 1393). 유지.
- `LegalFooter` 컴포넌트가 결과 화면에 일관 표시.

**보강 권장**:
- `powerImbalanceDetected === false`여도 결과 화면 하단에 "이 결과가 마음을 무겁게 한다면" 같은 자원 카드를 *상시* 두는 것을 검토. 강제는 아니지만 항상 *보이는 위치*에.

### 4.5 WCAG 2.2 신규 cognitive 항목 적용

다음 항목은 다시봄의 모든 화면에 적용되며, 결과 리포트에서 특히 중요합니다.

- **3.2.6 Consistent Help**: 도움말·핫라인·종료 버튼은 모든 화면에서 같은 위치에 있습니다. `LegalFooter`가 결과 화면에서 일관 위치 — 양호.
- **3.3.7 Redundant Entry**: 같은 정보를 두 번 묻지 않습니다. 닉네임, 관계 유형은 store에서 자동 채워짐 — 양호.
- **3.3.8 Accessible Authentication**: 매직 링크, OAuth, 이메일 인증코드 — 비밀번호 기억·시각 퍼즐 강제 없음. 양호.
- **2.5.8 Target Size (Minimum)**: 모든 탭 가능한 요소는 24×24 CSS pixels 이상. PR 시 점검.
- **2.4.11 Focus Not Obscured (Minimum)**: 키보드 포커스가 sticky header/footer로 가려지지 않습니다 — 채팅 화면 sticky 영역 확인 필요.

### 4.6 색맹·저시력 사용자 검증

A 피치(`var(--P-a)`), B 세이지(`var(--P-b)`)의 구분은 적록 색맹 사용자에게 모호할 수 있습니다.

**원칙**:
- 모든 색상 기반 구분은 *형태·라벨로도 동시에* 구분됩니다. `MessageBubble`에서 isMine은 좌·우 + 색상으로 이중 구분 — 양호. `NeedsMap`에서 두 점은 색상 + 라벨(`labelA`, `labelB`) 동시 사용 — 양호.
- Figma·브라우저 plugin 등에서 colorblind simulation으로 PR 전 검증합니다.

## 원칙군 사이의 충돌 해결

원칙들이 충돌할 때 다음 우선순위를 따릅니다.

1. **위기 사용자 보호** > 다른 모든 것
2. **AI 신뢰성** > 인지 부하 최소화 (HAX G1 한계 진술은 단계 하나가 늘어나도 둡니다)
3. **인지 부하 최소화** > 결과 해석 풍부함 (수치 설명을 더 보여주려고 화면을 복잡하게 만들지 않습니다)

## 적용 우선순위 및 로드맵

본 문서의 모든 원칙을 한 번에 적용하지 않습니다. 다음 4단계로 점진적으로 도입합니다. **현재 코드베이스 진단**에 따라 갭이 있는 항목을 1순위로 둡니다.

### Phase 1 — 즉시 (1군 + 2군의 *현재 갭*)

- §2.3 **위기 모달 dismiss 마찰 복원** — `chat/CrisisModal.tsx`의 `onClick={onClose}` 제거 + `shared/CrisisResourceModal.tsx`의 ESC 핸들러 수정. 두 모달 거동 통일.
- §1.1 AI 능력·한계 카드 — `/session/chat/[id]` 첫 진입 1회 노출. 현재 `EmptyChatPlaceholder`에 한 줄 추가가 가장 자연스러운 위치.
- §2.1 PR 템플릿에 4개 질문 추가.

### Phase 2 — 보강

- §1.2 `EmptyChatPlaceholder`에 "정리가 어색하면 이어서 말씀해 주세요" 카피.
- §1.3 `NeedsMap` 점 옆 `?` 아이콘 추가 (G11 보강).
- §1.4 `ChatHeader`에 "이 세션 그만두기" 메뉴 추가.
- §2.2 `ChatInput`에 "이 글은 AI가 정리해서 전달돼요" 작은 안내.

### Phase 3 — 카피·인터랙션 디테일

- §3.4 감정 부하가 큰 버튼 라벨 audit + 일괄 교체.
- §2.7 4개 stress 시나리오를 PR 체크리스트에 정착.

### Phase 4 — 결과 리포트 폴리싱 (4군)

- §4.5 WCAG 2.2 신규 항목 audit + 수정 (특히 채팅 화면의 sticky/포커스).
- §4.6 colorblind 검증 자동화.
- §4.4 결과 화면 상시 자원 카드 (`powerImbalanceDetected === false` 시).
